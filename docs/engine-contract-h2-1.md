# EngineAdapter v0 — H2.1 (Archi #17 / Eugenia #18)

[Contrato temprano compartido](https://github.com/Montara-Projects/MONTARA-BRAIN/issues/18#issuecomment-7178596487), [ADR #415](https://github.com/Montara-Projects/Montara/issues/415#issuecomment-7141340666), [H0 Eugenia](https://github.com/Montara-Projects/MONTARA-BRAIN/issues/1#issuecomment-7150771137), [fixture JM #417](https://github.com/Montara-Projects/Montara/pull/417) como referencia no dependencia. No freeze público.

`montara_core.domain.execution`: frozen InputFile(representation_id, path, sha256, size_bytes), Shot(representation_id, start_ms, end_ms), OutputProfile(1920,1080,30,h264,aac,mp4), ExecutionSpec(job_id, task_id, attempt_id, generation, recipe_revision_id, inputs, master_representation_id, shots, profile, workspace), EngineCandidate(path, sha256, size_bytes, engine_version, engine_revision). `montara_core.application.engine_port.EngineAdapter.execute(spec) -> EngineCandidate` síncrono. InputFile.path es copia privada verificada y absoluta, no una ruta del usuario; sólo originales locales, no proxies. Shots secuenciales de velocidad 1, intervalos [start,end) en ms de fuente sincronizada, master continuo t=0 por suma de duraciones. No inferir sincronía ni recortar silenciosamente; adapter valida duración, tipos y capacidad real. Profile único inicial. Engine puede usar stages internos sin conocer SQLite, owner, auth o publicación. El candidato MP4 debe quedar dentro del workspace exclusivo y acompañarse del manifest mínimo (digest/tamaño/pin/version); no sustituye la comprobación independiente audiovisual.

La autoridad Core emite ref exacta y staging de snapshot inmutable; rechazo de stale attempt antes y tras staging. Resultado sintético prohibido para export, sin success real ni publicación por ahora. H2 siguiente requiere verificar candidato (bytes, confinamiento, contenido), revalidar permisos/fencing en commit, promover artefacto privado reconciliable y guardar receipt, manejar crash/huérfanos y límites de admisión/espacio. No afirmar exactly-once externo. El workspace es desechable y privado; recuperación requiere un nuevo intento, no se reutilizan copias del previo. Retención/limpieza post ejecución pendiente de integración; fallo de staging limpia sólo su workspace nuevo. Operador debe aislar las raíces de otros usuarios locales y no modificar las copias mientras el worker las consume.

Task única export es DAG finito trivial y suficiente para el primer MP4; no plataforma de etapas distribuidas. Persistencia v3 mantiene una Task por Job y Attempt FK a Task; estado agregado identidad, ambos actualizados transaccionalmente. Receta y originales inmutables por API, snapshot del job fijado en task; las revisiones antiguas siguen disponibles para jobs existentes y no se reinterpretan. Nuevo job con receta/representación obsoleta rechazado; replay idempotente del job antiguo sigue válido. Futuros cambios de semántica deberán versionar contratos y migraciones.

No OIDC ni HTTP de medios/jobs, no Engine, Mixer, optimización ni transferencia cloud en H2.1. H2 completo aún exige autenticación real, publicación/MP4 real, QA de contenido, release y recuperación operativa.

## Restricciones de admisión del perfil inicial — BRAIN #21 / QA B

[Alineación Archi/Eugenia](https://github.com/Montara-Projects/MONTARA-BRAIN/issues/21#issuecomment-7179422844), [ACK Eugenia](https://github.com/Montara-Projects/MONTARA-BRAIN/issues/21#issuecomment-7179354145), [validator upstream fijado](https://github.com/Montara-Projects/Montara/blob/1fb15f87eb8df9e1ac08123fb7a8e79ffad1c24d/companion/video_recipe.py). El subconjunto Core se limita a 1–1000 shots, hasta 200 representaciones cámara distintas, extremos enteros múltiplos de 100 ms (3 frames exactos a 30fps), 0 ≤ inicio < fin ≤ 86.400.000 ms, duración positiva por shot y total ≤ 21.600.000 ms. No ampliar a 2000 shots de upstream. Sin redondeo, recorte, splitting ni reordenación. Perfil exacto 1920×1080/30, H264/AAC MP4, velocidad 1, master desde cero.

Core exige al menos una ubicación nominal MP4/MOV de cámara y WAV de máster (sufijo insensible a mayúsculas). Catalogar otras extensiones sigue permitido, pero no habilita receta/export. Selección de staging únicamente entre ubicaciones nominalmente admitidas de **la misma representación**, con digest/tamaño verificados; no renombrar MKV/MP3 u otros formatos ni usar un proxy. El sufijo no verifica contenido: adapter exige H264 plano CFR30, sin rotación/360, dimensiones y PTS conforme a su preflight; máster WAV PCM entero y cobertura real de muestras, cobertura efectiva de cámaras y decode. No confiar duración de contenedor ni introducir relleno. Esos checks de contenido siguen siendo responsabilidad del adapter, no de esta validación determinista.

Validación al guardar revisión, crear un job nuevo y preparar ExecutionSpec antes de crear workspace. Esquema SQLite v3 intacto. Recetas/job históricos permanecen legibles; replay exacto de create conserva el recibo anterior, no implica elegibilidad. Un snapshot legado incompatible no se ejecuta: prepare_execution devuelve error controlado, sin workspace ni resultado; el operador puede finalizar ese intento como failed/cancelled según contrato existente. Para corregir, guardar explícitamente una nueva revisión con CAS y crear nuevo job/clave, nunca modificar snapshot antiguo. Un job histórico válido conserva sus referencias exactas aunque ya exista revisión posterior. No auto-migración de tiempos o formatos.

**Semántica Stage pendiente de decisión explícita:** sin efectos manuales no implica salida neutral: Eugenia ha verificado que la ruta fijada aplica fundidos extremos/color matching por defecto. No se modifica ni se declara aceptada esa semántica aquí; Alfred debe resolverla antes del merge/integración del adapter. No monkeypatch ni reinterpretación de recetas.
